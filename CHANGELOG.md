## [0.42.0] - 2026-11-06

### Added

- **cognovis/fhir-billing-core#16**: a draft 2020-12 JSON Schema for `BillingRuleSet` files and the rule-set Library payload (`$defs/libraryPayload`), `$id` `https://fhir.cognovis.de/billing-core/schema/billing-rules/v2` (`BILLING_RULE_PAYLOAD_SCHEMA_URI`). Each of the 16 known rule classes has its own `parameters` schema selected by `class`; `factSources` and `appliesTo` are covered; a rule of an unknown class is accepted with any `parameters` object, as the decoder accepts it (the engine then refuses it when `mustUnderstand` is true). Constraints the schema cannot express (unique ids, period order and the like) are listed in `$defs/decoderOnly`.
- The schema ships in `@cognovis/fhir-billing-rules` as the export `@cognovis/fhir-billing-rules/schema/billing-rule-set.schema.json` and as the release asset `billing-rule-set.schema.json`; the release workflow takes the asset from the packed rules archive and verifies its sha256 before attaching it.
- `decodeBillingRuleSet` accepts a non-blank `$schema` string in a bare rule-set file and drops it; it is never part of the payload digest. A rule-set Library payload carrying `$schema` is still refused.
- `tests/rule-set-schema.test.ts` judges a shared fixture set (one valid fixture per class and one per decoder rejection reason) with the schema and the decoder and requires identical verdicts. The README section "Rule classes" is generated from the schema by `scripts/rule-class-reference.mjs` and checked in `npm test`.
- `fhir-billing-check` accepts a file with `$schema` once its SDK in `cognovis/chp` runs on `@cognovis/fhir-billing-rules` 0.42.0 or later. Published under the fresh `fbc-16-billing-0-42-0` npm tag.

## [0.41.0] - 2026-11-05

### Added

- **cognovis/fhir-billing-core#127** (ADR-005): contract-bound catalog editions. A native edition's manifest can name the Contract canonicals whose own tariff it is in `contracts` (`url` or `url|version`, unique); `buildBillingLibrary` writes one `depends-on` related artifact per Contract, and `decodeBillingLibrary` refuses an edition whose `depends-on` links are not exactly its manifest's Contracts, including one bound by only one of the two. A bound edition is built from its whole inventory (`catalogDefinitions`, plus `ruleSet` and `configuredRules` for its Library members); any other member is refused. Each catalog definition entry of a bound edition carries the definition's billed coding in the new extension `BILLING_CATALOG_DEFINITION_CODING_EXTENSION` (`catalog-definition-coding`, in the IG). The member-set digest covers the sorted Contracts and each entry's coding as `{ scheme: 2, members, contracts }`, so the admission record binds the Contract assignment and the codings the edition holds; an unbound edition keeps its digest and needs no re-admission. `billingCatalogEditionDigest` takes the Contracts as an optional second argument.
- The SDK selects a contract-bound edition only for a case whose Applicable Contract it is bound to: for each billed coding, the bound editions that hold it (by an admitted entry coding or a found member definition) are its only candidates, otherwise the unbound editions are, as before. An edition bound to other Contracts is never a candidate, also not through an explicit `catalog`; such an edition and its admission record are evidence when it holds a billed coding. When several editions are in force, and for every edition an explicit `catalog` sets aside (outside the selector, or matching it but excluded by the Contract), every native edition an admission record of the tenant targets is digest-checked and must be bound by such a record before a result that relied on its members or Contracts is returned (one admission search per edition set aside, run at once and awaited after the selected editions are admitted); an edition no record of the tenant targets behaves as before, and an evaluation without a tenant that sets a native edition aside fails closed with `SNAPSHOT_UNAUTHORIZED`. An explicit `catalog` that selects another edition while an edition bound to the Applicable Contract holds a billed coding yields `SNAPSHOT_AMBIGUOUS`. Two overlapping in-force editions bound to the same Contract that hold the coding yield `SNAPSHOT_AMBIGUOUS`, also when one of them covers every billed coding; a versioned binding to a Contract without `version` yields `SNAPSHOT_INCOMPATIBLE` (`contract-version-missing`). `selection.contractBoundEditions` (`BillingContractBoundEditionSelection`) names the edition and binding of every line a bound edition evaluates. Every in-force candidate edition is now read in full before selection, also a single one.
- SDKs before 0.41.0 refuse a contract-bound edition; producers upgrade before they load one. Published under the fresh `fbc-127-billing-0-41-0` npm tag; `latest` and the GitHub latest release stay where they are.

## [0.40.0] - 2026-11-05

Delivers cognovis/fhir-billing-core#196 of the Billing Core 0.34 batch cognovis/fhir-billing-core#187: the remaining EBM case kinds.

### Added

- **cognovis/fhir-billing-core#196**: four counting pairs that span Accounts, built on the same case grouping as the Behandlungsfall of 0.39.0:
  - `quarter`/`patient-per-site-and-insurer` is the Betriebsstättenfall (EBM I 3.3). It groups by site (`ChargeItem.performingOrganization`) and insurer, whoever performed the line.
  - `quarter`/`patient-per-physician-number-and-insurer` is the Arztfall (EBM I 3.4). It groups by physician number and insurer, independent of the site. The physician number is the one identifier value of the line's single performing Practitioner in the systems the host passes in the new optional input `physicianNumber: { systems }`. A German host passes the LANR systems.
  - `quarter`/`patient-per-practice-physician-group-and-insurer` is the Arztgruppenfall (EBM I 3.5). It groups by KV-Arztpraxis, physician group and insurer. The physician group is the one `PractitionerRole.specialty` code, in the system of the new optional input `physicianGroup: { system }`, on the performer's in-force roles at the line's site. The SDK searches `PractitionerRole?practitioner=..&organization=..` for it. A German host writes the EBM Arztgruppe there.
  - `day`/`patient-per-practice` is the Behandlungstag (EBM I 3.8.5). It groups by KV-Arztpraxis and calendar day, whatever the insurer. The day is `ChargeItem.occurrence`; for in-vitro diagnostics the writer records the specimen-collection date there.

  Exported types: `BillingPhysicianNumber`, `BillingPhysicianGroup`. An unknown site, practice, physician number, physician group or insurer fails closed with `COUNTING_SCOPE_UNAVAILABLE`, exactly as for the Behandlungsfall. This also covers a line of another Account that cannot be ruled out and a line whose date cannot be placed in the window. Every Practitioner and role read is evidence. Existing pairs keep their meaning, including `day`/`patient`.
- **cognovis/fhir-billing-core#196**: the advisory reason `ACCOUNT_OWNER_PRACTICE_DIFFERS` with `details` `{ owner, ownerPractice, practice }`. It appears when a rule set uses a pair keyed by KV-Arztpraxis and the evaluated Account's owner belongs to another KV-Arztpraxis on a line's service date than the line's site. Like `CATALOG_PARTIAL` it accompanies an `allow` or a rule `block` and never changes the decision or the resolved KV-Arztpraxis. An owner whose practice is unknown or cannot be read gives none. The reason is added to the `billing-reason` CodeSystem and `BILLING_REASON_CODES`. Consumers that switch exhaustively on reason codes must handle it.

### Fixed

- Charge retirement now also searches the patient's billed lines without any occurrence, and keeps a neighbor line whose date names no month as a possible target-quarter line. A case companion, the Behandlungsfall included, is therefore never retired while such a dependent may share the case. Such a line on an Account the SDK cannot read makes the retirement `unavailable`.

Published under the fresh `fbc-196-billing-0-40-0` npm tag. `latest` and the GitHub latest release stay where they are.

## [0.39.0] - 2026-11-05

Delivers cognovis/fhir-billing-core#147 of the Billing Core 0.34 batch cognovis/fhir-billing-core#187 (counting scope: the Behandlungsfall).

### Added

- **cognovis/fhir-billing-core#147**: the counting pair `quarter`/`patient-per-practice-and-insurer`, the EBM Behandlungsfall (EBM I 3.1, BMV-Ä §21 para. 1): the lines of one patient at sites of one KV-Arztpraxis in one calendar quarter under one insurer count together across Accounts, so two Scheine of one case cannot each bill a once-per-case GOP. A line's site is only its `ChargeItem.performingOrganization`; its KV-Arztpraxis is the `organization` of the site's one in-force `OrganizationAffiliation` with a practice-membership code whose period contains the service date, never a BSNR or the Account owner. Core names no membership code: the host passes them in the new optional input `practiceMembership: { system, codes, otherCodes? }` (exported type `BillingPracticeMembership`); a German host on de.cognovis.fhir.praxis 0.101.12 passes the `organization-relationship` system with `kv-arztpraxis-membership` and `uebag-membership` as codes and `company-membership` as other code. The insurer is the payor of the Coverage each line's Account selects on its service date. No, several or an unknown-coded membership, a line without `performingOrganization`, or an unknown or incomparable insurer returns `unavailable` with `COUNTING_SCOPE_UNAVAILABLE`. `BillingSnapshotProfiles` gains the optional `organizationAffiliation` descriptor; without it or without `practiceMembership` every rule of the pair is `unavailable`. The SDK searches `OrganizationAffiliation?participating-organization={site}`, searches the patient's billed ChargeItems without any occurrence (`occurrence:missing=true`), and reads other Accounts and their Coverages only when a rule set uses the pair; a billed line of the patient whose service date names no month is uncertain in every case it may belong to; every such read is evidence and the search a receipt. Existing pairs, `treatment-case`/`patient` included, keep their meaning. Charge retirement does not resolve the pair: retiring the required companion of a dependent that may share the case is `unavailable` there.

## [0.38.0] - 2026-11-05

### Changed

- **cognovis/fhir-billing-core#131** (child of cognovis/fhir-billing-core#187): the native fact `patient.age` is the completed age on the line's service date in every unit an age bound uses, `[{ value, unit: 'a' }, { value, unit: 'mo' }, { value, unit: 'wk' }, { value, unit: 'd' }]`, instead of whole years alone. A month is completed on the day of a later month with the birth day's number, or on the first day of the next month when that month is shorter (born 31 January: 0 months on 28 February, 1 on 1 March); a week is 7 completed days; the birth date is day 0. A `patient-attribute-constraint` bound compares against the quantity in its own unit, inclusive on completed units, never against a conversion: 01715- and 01717-shaped month bounds and 01709-shaped day bounds are decided, and a 34-month-old (2 years) no longer passes a 26-month maximum. Year bounds keep their verdicts. A partial or missing birth date stays `source-unavailable` in every unit. The engine compares a quantity-list fact only member by unit: a bound in an unlisted unit, an invalid member or a repeated unit is `PATIENT_ATTRIBUTE_UNIT_UNAVAILABLE`; a single quantity is compared as before. Consumers that read `case.facts['patient.age']` or a line's `patient.age` as one `{ value, unit }` must read the list. An older engine reads the list as no quantity and fails closed. Published under the fresh `fbc-131-billing-0-38-0` npm tag; `latest` and the GitHub latest release stay where they are.

## [0.32.0] - 2026-10-24

### Changed (breaking)

- **cognovis/fhir-billing-core#165** (security review F1/F2, [ADR-002](docs/adr/ADR-002-member-set-digest-scheme-2.md)): a native catalog edition's member-set digest, the one an admission record binds, is scheme 2 (`billingCatalogEditionDigest`). It covers each catalog definition's content digest (`billingCatalogDefinitionDigest`, extension `catalog-definition-digest` on the definition's `composed-of` entry) and each definition's configured-rule members digest. An admission therefore binds every definition's prices and which configured rules depend on each definition.
  - A definition of a native edition is used only with the content its edition entry names. A price changed in the store is `DIGEST_MISMATCH`, also when the definition's own `catalog-digest` identifier was recomputed.
  - A configured rule moved away from a billed definition, with the edition's members digests rewritten, changes the admitted digest and is `SNAPSHOT_UNAUTHORIZED` (`admission-missing`).
  - `buildBillingLibrary` requires `catalogDefinitions` (every ChargeItemDefinition member) for a catalog edition.
  - **Hard cutover:** an edition still carrying a scheme-1 digest is `SNAPSHOT_UNAUTHORIZED` with the new explanation `edition-digest-outdated`. `decodeBillingLibrary` refuses it with the cause `digest-scheme-v1`. Every native edition must be re-imported by its producer and re-admitted per tenant before a host adopts 0.32.0. Legacy editions keep scheme 1.

## [0.31.2] - 2026-10-23

### Fixed

### Breaking changes / migration

- **cognovis/fhir-billing-core#124**: The SDK decides a booking from FHIR alone. ## [0.24.5] - 2026-10-10

### Fixed

- **cognovis/fhir-billing-core#116**: An EBM evaluation with genuine billing entitlements no longer asks the tenant entitlement policy one request after another. An edition without a rule-set member is entitled by one `configured-rule` request per configured rule used (0.24.0), and the SDK awaited them sequentially: one EBM preflight for 51030+51032 made 168 sequential policy calls and took over 200 s, so a booking behind a 150 s gateway timeout failed. Now `evaluateBillingAccount`, `evaluateProspectiveCharge` and `evaluateCandidateCharges` (across all its candidates) send each distinct entitlement request to `policy` at most once per call, and ask the catalog-edition request and every rule request of an edition, and the editions of a multi-edition Schein, concurrently, at most `entitlementConcurrency` at once. The new optional input `entitlementConcurrency` (exported default `DEFAULT_ENTITLEMENT_CONCURRENCY`, 2) bounds the requests in flight to `policy` within one call; a value that is not a positive safe integer throws `BillingInputError`. Each request may wait up to about `entitlementConcurrency` times the resolver's per-request time, and the speed-up depends on the resolver serving requests concurrently: a host raises the bound only when its resolver answers concurrently and its transport timeout covers that wait (against a resolver that answers one request after another at about 1.1 s each, a bound of 8 made a 5 s capability timeout abort 164 of 168 requests). The default of 2 stays until the reference-data adapter answers faster: with adapter 0.1.25, `billing-entitlements.resolve` takes about 1.1 s per request and answers one request at a time, so the 51030+51032 preflight still takes about 165 s (187 s with 0.24.4). The bound may go up only once https://git.cognovis.de/cognovis/reference-data-adapter/issues/143 makes `resolve` fast and concurrent; the goal of a preflight below 60 s is tracked there. Every configured-rule member is still entitled by its own request (canonical, version and configured-rule digest); no request is merged or dropped, and no answer outlives the call. Verdicts are unchanged: the rule-set axis is entitled only when every rule request is, and when requests fail the evaluation fails with the failure of the first in order, edition by edition (an edition's catalog-edition request, then its rule requests, then the next edition's), whichever the policy answers first; that failure decides as soon as it and every earlier request are answered, without waiting for later ones, and the rule sets of editions admitted before it stay attested. Each answer is copied before the next request may reach the policy, the caller's input is read as given (inherited fields included, `policy.tenant` read when each request is built) and a `null` policy behaves as before. A policy may now receive further requests, of the same or a later edition, after one of them failed. Consumers need no change; a host whose policy cannot take parallel requests sets `entitlementConcurrency: 1`. The README describes this in "Entitlement requests". `tests/sdk-entitlement-requests.test.ts` covers one policy call per distinct request within each operation (a rule set two editions share), one request per configured-rule member with its own canonical, version and digest, the in-flight bound (3 of 11, the default 2), invalid bounds, a denied member and a failing member giving the sequential verdict, the earliest failure in order winning, an earlier failure deciding while a later request never answers (within an edition and across editions, at concurrency 1 and the default), an earlier edition's attestation kept, a policy that reuses one decision object, an input with inherited fields, a live `tenant` getter, a `null` policy on legacy carriers, and wall time following the bound (17 requests of 40 ms at concurrency 4 in about five rounds).

### Fixed

- **cognovis/fhir-billing-core#106**: Billing SDK searches longer than one page read completely from Aidbox 2608.1. Its paging links name the container-internal origin (`http://aidbox:8080/fhir/...&_page=2`), which `@cognovis/fhir-sdk` refuses as a continuation that leaves the configured FHIR origin, so every search longer than one page was `unavailable` with `SNAPSHOT_MALFORMED` (`fhirSdkCode: transport`, explanation `fhir-request-failed`): every billed EBM code with more than 100 configured-rule Libraries, such as 51030 with 167, could not decide. `searchResources` still follows the store's `next` links as long as fhir-sdk accepts them, so a standard store that pages through its own continuations and ignores or rejects `_page` needs nothing else. When fhir-sdk refuses a continuation before sending it (an `FhirSdkError` with code `transport` and no HTTP status, classified from its structured fields), or when a page has no `next` link while the known total (accurate, else the largest advisory one) exceeds the results collected (Aidbox answers Library searches without paging links), the SDK requests the remaining pages itself as the same query with Aidbox's 1-based `_page` parameter and never follows a server URL for that search again. The supported store contract for that fallback is `_page` with a page size that stays the same between requests and a page past the end answered with no entries. Completeness is proven only by an accurate total the results equal, by the end of the `next` chain, or, paging by number without an accurate total, by an empty page past the end; an advisory total never ends paging by number, and the results must reach the largest one stated. The search fails closed with `SNAPSHOT_PAGINATION_INCOMPLETE` for a repeated resource (a store that ignores `_page` repeats its first page), a page that adds nothing while an accurate total is unmet, results short of the largest advisory total, and a search that states no total; with `SNAPSHOT_MALFORMED` (or the typed failure of its HTTP status) for any other failure of a `next` request, a rejected `_page` request and a malformed `next` link; and with `SNAPSHOT_PAGINATION_LIMIT` beyond 20 pages. The first request, the search receipts (which record the first page's query) and single-page searches are unchanged; paging by number without an accurate total costs one extra request for the empty page. Residual, as before: a single link-less first page whose results reach an understated advisory total is accepted as complete. The README text on search completeness states the contract. `tests/sdk-far-canonicals.test.ts` covers a same-origin cursor `next` chain with `_page` rejected (HTTP 400) or ignored, a failing `next` request without fallback, the container-internal origin falling back to `_page` and deciding as the runtime store, a rejected `_page` after that fallback, link-less pages with a larger and with an understated advisory total read to the empty page, a store that keeps answering past the page limit, and a store that ignores `_page`; `tests/sdk-configured-rule-edition.test.ts` covers a link-less configured-rule search (`identifier=...|configured-rule` with `depends-on`) with an accurate total and with `_total` refused by HTTP 500 and an exact or understated total, deciding `allow` and `block` as the unpaged store, and failing closed when the store states more results than it serves.

## [0.23.0] - 2026-10-07

### Added

- **cognovis/fhir-billing-core#47**: A host can run overlay rule sets, rule sets a third party maintains beside the fee schedule's own rule set (for example a practice's own deterministic check of its fee schedule), and gets each overlay's verdict with its publisher. An overlay is a native rule-set Library bound to the catalog edition(s) it applies to in two parts that must agree, as a contract rule set is bound to its Contract: the digest-covered payload member `appliesTo.catalogEditions` (a non-empty list of unique catalog-edition canonicals, `url` or `url|version`) and one `depends-on` related artifact per entry; it is never a `composed-of` member of the edition. The carrier codec refuses links that name other editions than the payload and an `appliesTo` that names both `contracts` and `catalogEditions`. The host requests overlays with the new optional input `overlays: [{ ruleSet, role? }]` (`BillingOverlayRequest`, `role` `advisory` by default or `gate`) on `evaluateBillingAccount`, `evaluateProspectiveCharge` and `evaluateCandidateCharges`; the SDK never runs an overlay it was not asked for. Each overlay is read with one exact `Library?url=...[&version=...]` search (active-copy rule of #34, active and in force on every service date), checked against the editions selected for the Schein's lines, digest-checked, entitled through the tenant policy (`artifactKind: 'rule-set'`, canonical, version, digest, publisher, no sources) and evaluated on the lines of the editions it is bound to, with the same projected case (facts, counting windows, per-line data) as the fee schedule's rule set. It inherits the catalog admission of its bound edition: a partial edition adds `CATALOG_PARTIAL` to the overlay's `allow` or `block`, an edition that is not admitted (not entitled, unknown completeness, outside its period) makes the overlay `unavailable` with the withheld reason, so a gate never blocks over catalog data its edition does not admit. A cross-Account history needed only by overlays (or only by contract rule sets) is projected only into the rule sets that need it, inside their own failure boundary: a failed history search or an unreadable history line (for example quantity -1) is their `unavailable` verdict, and the fee schedule's rule sets project the history only when they need it themselves. `url` and `url|version` requests of the same canonical url are one overlay requested twice and fail the call as malformed. The result's new `overlays` (`BillingOverlayVerdict[]`) holds one verdict per request: `ruleSet`, `role`, `decision`, `reasons` (with `ruleId`, `sources` and `evidenceLevel` of the overlay rule, `details.ruleSet` naming the overlay on every reason of a `block` or `unavailable` verdict except `CATALOG_PARTIAL`, engine-withheld reasons included, and an `explanation` on every reason of an `unavailable` verdict), `canonical`, `version`, `digest` and `publisher` (only once the overlay decoded, matched its digest and was entitled). An `advisory` overlay never changes `decision`; a `gate` overlay's `block` makes `decision` `block` (its reasons name the overlay in `details.ruleSet` and `details.overlay: 'gate'`), and its `unavailable` makes `decision` `unavailable` unless another rule set already blocks. An overlay that is not entitled (`EDITION_UNENTITLED`), applies to no selected edition (`SNAPSHOT_INCOMPATIBLE`, `overlay-edition-not-selected`), fails its digest (`DIGEST_MISMATCH`), is missing (`SNAPSHOT_MISSING`, `overlay-missing`), not in force (`SNAPSHOT_STALE`), unbound (`overlay-not-bound`) or malformed is that overlay's `unavailable` verdict with its reason and explanation and, as advisory, leaves the decision unchanged. Every overlay read is in `snapshot.evidence`, the writer preconditions, the search receipts and the new `selection.overlays` (`BillingOverlaySelection`), also on an `unavailable` result and for a copy the version selection rejects (retired or ambiguous). When only a gate overlay reaches the decision, the new `selection.decisiveOverlay` names it, and the bundle record's `ruleSet` is that overlay, with the publisher of its verdict only. A bundle record now names a rule set's `publisher` only when the tenant policy entitled that rule set in the evaluation: an edition rule set or a decisive gate overlay the policy refused (or that failed its decode or digest) has no `publisher` in the record. When a failure stops the evaluation before the rule sets are evaluated, no `selection.overlays` or `selection.contractRuleSets` entry stays `evaluated`; such an entry is `unavailable`. `evaluateBundleConformance({ ..., overlays })` evaluates the overlays on every Account, the bundle client serves their search and `bundleEntitlementPolicy` entitles an overlay of the bundles; each record lists `overlays` (`BillingBundleOverlayVerdict`), which `compareConformanceRecords` ignores. Typed standalone evaluation and the `fhir-billing-check` CLI request no overlays. Seven explanation keys join `BILLING_UNAVAILABLE_MESSAGE_KEYS` (now 133): `overlay-request-invalid`, `overlay-missing`, `overlay-not-in-force`, `overlay-ambiguous`, `overlay-not-bound`, `overlay-edition-not-selected` and `overlay-in-edition` (an edition whose rule-set member is an overlay, `SNAPSHOT_INCOMPATIBLE` with `details.unsupported: 'overlay-rule-set-member'`). README "Overlay rule sets", the GLOSSARY entry "Overlay rule set" and ADR-001 record the design. `tests/sdk-overlay-rule-set.test.ts` covers the carrier binding and its refusals, the advisory overlay that blocks a line beside an unchanged `allow`, the gate overlay that blocks and the one that cannot decide, the refusals (not entitled, another edition or edition version, digest mismatch, changed rules, link and payload that disagree, `contracts` beside `catalogEditions`, an unbound rule set, a missing and a retired overlay, malformed requests), the evidence, receipts, selection and writer preconditions, a later failure that keeps the overlay read, lines of two editions, candidate charges equal to single calls, one added request per overlay on a 3-member and a 2,003-member edition alike, the bundle record and an overlay as an edition member, and the repair cases: a malformed history line needed only by an overlay (advisory: decision unchanged; gate: a fee-schedule block stays), retired overlay copies as evidence, overlay and contract rule-set status after an early failure, the publisher of a forged Library with a tampered digest, the admission inherited from a partial, an unentitled and an unknown-completeness edition, the `appliesTo` union type, `decisiveOverlay` and the bundle record's decisive rule set, `url` beside `url|version` requests, and `details.ruleSet` on every verdict reason.

## [0.15.0] - 2026-10-07

### Fixed

- **cognovis/fhir-billing-core#39**: The Billing SDK derives the counting windows rules name by `countingScope` `{ window, subject }`, so counting-scoped rules decide instead of returning `COUNTING_SCOPE_UNAVAILABLE`. Before, the SDK keyed every window by the raw service date and Patient reference (`{ window: '2026-08-14', subject: 'Patient/x' }`), which never matches the window vocabulary, so every counting-scoped rule, for example the EBM once-per-session quantity limits, was `unavailable`. The engine contract is unchanged: windows are `{ scope, lineIds }` matched exactly against `rule.parameters.countingScope`. Derived (README, "Counting windows"):
  - `session`/`patient`: lines with the same Encounter in `ChargeItem.context` and the same patient. A line without a literal `Encounter/{id}` context cannot be placed, and the session is never guessed from the date.
  - `day`/`patient`: lines with the same service date and the same patient, counting the patient's `billable` or `billed` ChargeItems of that date on other Accounts (the quarter search below).
  - `quarter`/`patient`: lines of the same calendar quarter and patient, counting the patient's `billable` or `billed` ChargeItems of that quarter on other Accounts. These are read with `ChargeItem?patient=&occurrence=ge&occurrence=le&status=billable,billed`, paged to completion or failed closed. The bounds are one day wider than the quarter on each side, and the SDK keeps only lines whose local service date lies in the quarter, so a server comparing an offset datetime in UTC cannot drop a boundary line.
  - A history line counts when every account reference is assigned to another Account of this server: a literal relative `Account/{id}`, its versioned form `Account/{id}/_history/{v}`, or either as an absolute URL under the new optional input `fhirBaseUrl`. A line with a reference to the evaluated Account is that Account's. A line without an `account`, or with any reference the SDK cannot assign (another server's URL, an absolute URL without `fhirBaseUrl`, a contained or identifier-only reference), is never ignored: every rule it and an Account line of its day or quarter window take part in is `unavailable` with `COUNTING_SCOPE_UNAVAILABLE` for that window.
  - Of the Account's own lines only the prospective charge and stored lines with status `billable` or `billed` count in windows; `entered-in-error`, `not-billable`, `aborted` and `planned` lines take no place in a window.
  - `quarter`/`patient-per-physician`: as `quarter`/`patient`, per single performing Practitioner (`ChargeItem.performer[].actor`), across practices insofar as the store holds their lines. When any line of the patient's quarter has no performer, several Practitioners, or any performer that is not a literal relative `Practitioner/{id}` reference (PractitionerRole, absolute or versioned URL, identifier, another resource type), the physician is unknown and the window is unavailable.
  - Every other window or subject (`treatment-case`, `rolling-days`, `calendar-year`, `tooth`, ...) and every scope that carries a `qualifier` stay `unavailable` with `COUNTING_SCOPE_UNAVAILABLE`. No Core or DE profile marks an Account as a treatment case, and the adapter defines the `rolling-days` qualifiers (`anchorSection`, `windowMultiple`, `anchorDirection`) only structurally. The engine ignores a qualifier when it matches, so a qualified scope gets no window.
  - The rule set is compiled and admitted once as a whole: a rule set admission withholds (for example `UNSUPPORTED_RULE`) is `unavailable` before any window is derived, and a counting-scoped rule of it never blocks.
  - Because the engine admits one window per scope per case and an Account holds several sessions, days or quarters, a rule set with counting-scoped rules is evaluated in parts. The rules without a counting scope run once over the Account's lines; the rules of each counting scope run once per derived window over that window's lines; and the lines a scope cannot place run together without a window. A `mutual-exclusion` or `companion-required` rule (or a rule class the SDK does not know) that an unplaced line takes part in is `unavailable` with `COUNTING_SCOPE_UNAVAILABLE` for the scope when a line it could share a window with takes part too, or those lines were not all read, so an excluded code without an Encounter beside the selecting code is never `allow`. The other classes read only selected lines, whose unplaced evaluation is already `COUNTING_SCOPE_UNAVAILABLE`. The results combine by the effect the engine gives each finding, never by the rule's `effect`: any rejecting finding is a `block`, else any review finding is `unavailable`, else `allow`. So `ACTUAL_MULTIPLIER_UNAVAILABLE` of a rejecting rule is `unavailable`, and a threshold finding has its `aboveThresholdEffect`. A rule set without counting-scoped rules is evaluated exactly as in 0.14.0.
  - Lines of other Accounts join only day and quarter windows, only of the evaluating edition's own coding systems (a GOZ quarter limit counts GOZ history, never GOAE). In such a window a finding naming an Account line counts; a finding naming only another Account's line, or no line, counts only when an Account line of the window takes part in the rule (the rule selects, excludes or requires its code) and the rule names no Account line itself. So an Account line that another Account's line excludes in the quarter blocks, while another Account's own excess, a conflict only between other Accounts, or a missing fact of a rule only other Accounts' lines meet does not decide this Account.
  - Every history ChargeItem read is versioned runtime evidence in `snapshot.evidence` and an `If-Match` writer precondition. Its search is receipted, so a line billed concurrently on another Account invalidates the writer through `assertWriterSnapshot`. History is read only when a rule set uses a window spanning Accounts.

## [0.11.0] - 2026-10-06

### Added

- **cognovis/fhir-billing-core#38**: Canonical-and-digest evidence for catalog members the store does not version. A catalog-edition, rule-set or configured-rule Library, or a catalog-member ChargeItemDefinition, without `meta.versionId` is recorded as the new `CanonicalDigestEvidence` `{ resourceType, id, canonical: 'url|version', digest: 'sha256:<hex>', sourceReference }`. `digest` is the sha256 of the canonical JSON of the resource without `text` and without the volatile store fields of `meta` (`versionId`, `lastUpdated`, `source`, and `extension`, where Aidbox keeps `createdAt`); `meta.profile` (sorted) and every other `meta` field stay covered, because `meta.profile` decides edition detection and the artifact-locator check. The configured-rule Libraries the rule-set selection reads are bound into `snapshot.evidence` and `writer.preconditions` like the rule-set Library, because they decide which edition member is the rule set; they do not take part in the artifact-locator check. Its receipt identity is `Type/id#<url>|<version>@sha256:<hex>`, and its writer precondition is `{ path: '/Type/id', canonical, digest }` without `ifMatch`. `BillingSnapshot.evidence` is now `readonly BillingResourceEvidence[]`, the union of `ResourceVersionEvidence` and `CanonicalDigestEvidence`; both carry the other's distinguishing keys as optional `never`, so `evidence.versionId !== undefined` narrows the union. `WriterPrecondition` gains the optional `canonical`.
- `verifyCatalogMemberPrecondition(precondition, reread)` returns `ok` only when a writer's re-read catalog member is the bound `Type/id`, still has the bound `canonical`, and has an unchanged content digest; anything else is `conflict`.

### Fixed

- **cognovis/fhir-billing-core#38**, folds **cognovis/fhir-billing-core#37**: The Billing SDK evaluates catalogs whose Libraries Aidbox serves from its package registry (`far`). Before, every such evaluation was `unavailable` with `SNAPSHOT_MALFORMED`. That covered every Aidbox 2608 installation whose reference data writes Libraries over REST, including the synthetic Reetfurt seed. The registry refuses `Library?...&_total=accurate` with HTTP 500, omits `entry.search.mode`, paginates under `links`, and serves no `meta.versionId`. Now:
  - A search whose `_total` is refused (HTTP 4xx or 5xx whose message or OperationOutcome names `_total`) is sent once more without it. The refusal is remembered per resource type for the rest of the evaluation, and the receipt records the query actually sent. An authorization failure (401, 403) and every other failure are never retried.
  - Without an accurate total, a stated `total` is advisory. Completeness rests only on following `next` to its end within the page limit: beyond it is `SNAPSHOT_PAGINATION_LIMIT`, a malformed `next` link is `SNAPSHOT_MALFORMED`, and a stated total larger than the collected results at the end is `SNAPSHOT_PAGINATION_INCOMPLETE`. A chain none of whose pages states a `total` is `SNAPSHOT_PAGINATION_INCOMPLETE` as well, because a dropped `next` link could not be told from the end; Aidbox's package registry always states one. This also covers the two fail-open risks found in the #37 candidate: a malformed `next` link taken as the end of the search, and an estimated total taken as exact.
  - Catalog members without `meta.versionId` carry canonical-and-digest evidence (see Added).
  - With `_total=accurate` honoured, the exact-total enforcement of 0.10.1 is unchanged. Runtime resources (Account, ChargeItem, Coverage, Contract, Observation, and any catalog member that has `meta.versionId`) keep `Type/id@versionId` evidence and `If-Match` preconditions exactly as in 0.10.1. Without `meta.versionId` they still fail closed with `SNAPSHOT_MALFORMED`.

### Changed

- `@cognovis/fhir-billing-sdk` peers on `@cognovis/fhir-sdk` `^0.15.9` (dev `0.15.9`). 0.15.9 accepts modeless searchset entries when no includes are declared, follows Aidbox's `links`, and raises on a malformed `next` link (cognovis/fhir-sdk#31).
- Consumer effect: MIRA and hkp writers must honour digest preconditions. A precondition with `canonical` and `digest` and no `ifMatch`/`ifNoneMatch` is checked by re-reading the member and calling `verifyCatalogMemberPrecondition` immediately before persisting; a `conflict` means do not persist and re-evaluate. After the commit the writer verifies every digest precondition once more; on a `conflict` it marks the persisted ChargeItem stale, re-evaluates and compensates it, and records that (README, "Writer contract for digest preconditions").
- Known residual: a digest precondition is a check-then-act in the writer without server-side enforcement and is not equivalent to `If-Match`. A catalog member replaced between the writer's last re-read and its commit is not refused by the store, so a ChargeItem can be persisted and invoiced against a superseded price or a rule that would have blocked it. ## [0.7.0] - 2026-10-04

### Added

- **cognovis/fhir-billing-core#17**: `evaluateBillingAccount` checks an existing Account and every ChargeItem returned by the `account=Account/{id}` search without a prospective charge. An Account without ChargeItems is checked at `asOf`, still passes the catalog-edition and rule-set admission gates, and evaluates no placeholder line. It returns resource-version evidence and search receipts, but no writer preconditions.
- **cognovis/fhir-billing-core#17**: Both operations select the Coverage in force and the applicable Contract for every service date (`occurrenceDateTime`, else `occurrencePeriod.start`) from `Account.coverage` and the selected `Coverage.contract`, and return a selection record naming the Account, service dates, Coverage and Contract (reference, `versionId`, canonical identity), catalog edition (canonical, version, member-set digest) and rule set (canonical, version, payload digest).

- The packed consumer (`scripts/packed-consumer/runner.mjs`) runs both operations outside the checkout with its own entitlement policy and canonical client and observes allow, block and unavailable for synthetic statutory-ambulatory, selective-contract, statutory-dental and private-dental cases.

### Changed

- Publish the four npm units at 0.7.0. `@cognovis/fhir-billing-sdk` keeps peering on `@cognovis/fhir-sdk` `^0.15.8`, the current latest.
- Contract participation in the engine case is the selected Contract's canonical identity (`Contract.url` and/or `Contract.instantiatesUri`) only. The SDK no longer reads Contracts referenced from ChargeItems, the prospective charge, `Account.extension` or `Account.contracts`, and no longer projects `Contract.identifier[0].value` or the Contract id.
- The README and CONTEXT document the account check, service-date selection, the selection record and the result union; the implementation plan names the canonical profile-bound client instead of a caller-injected transport.

### Breaking changes / migration

- `evaluateBillingSnapshot` is removed. Call `evaluateProspectiveCharge` and pass the ChargeItem as `prospectiveCharge` (was `prospectiveMutation`). `EvaluateBillingSnapshotInput` and `EvaluateBillingSnapshotResult` become `EvaluateProspectiveChargeInput` and `ProspectiveChargeResult`. Hosts that built a placeholder or zero-quantity ChargeItem to check an Account call `evaluateBillingAccount` instead.
- The result is a discriminated union on `decision`. Narrow before reading: `allow` and a rule `block` (`blockedBy: 'rule'`) always carry `case`, `ruleSet`, `admission` and a complete `selection`; a selection `block` (`blockedBy: 'selection'`) carries no case and a `selection` that ends at the blocking step; `unavailable` carries the parts resolved before the failure. Results now also carry `searches`; `evaluateBillingAccount` results carry no `writer`.
- Producers must link `Account.coverage[].coverage` to a Coverage with `status`, `period` and, where known, `beneficiary`, and link `Coverage.contract` to a Contract with `status`, `applies` and `url` or `instantiatesUri`. Accounts without that linkage, with several in-force Coverages that do not all carry distinct `Account.coverage.priority` values, with an Account subject and Coverage beneficiary that are not the same Patient reference (two relative `Patient/{id}` references match by id, two absolute `http(s)` URLs ending in `/Patient/{id}` only when identical, and an absolute reference never matches a relative one) while both sides are present, or with a Contract lacking a canonical identity now yield `unavailable`; a cancelled or out-of-period Coverage and a terminated, revoked, cancelled, rejected or out-of-period Contract yield `block`.
- Country `contract-participation` rule instances must set `parameters.contract` to the Contract's canonical `url` or `instantiatesUri`; an identifier value no longer matches.
- Every evaluated line needs a valid service date; a stored or prospective ChargeItem without a valid FHIR `occurrenceDateTime` or `occurrencePeriod.start` of at least a full date yields `unavailable` (`SERVICE_DATE_MISSING`). Coverage `period` and Contract `applies` bounds must be valid FHIR dates or dateTimes, else `unavailable` (`SNAPSHOT_MALFORMED`). A bound with a time is compared as an instant when it and the line carry zoned times; otherwise a timed bound on the service date makes the candidate indeterminate (`unavailable`). A prospective ChargeItem with quantity 0 or a non-integer quantity (`PROSPECTIVE_QUANTITY_INVALID`), or whose `ChargeItem.account` is missing, names another Account, or holds an entry without a literal reference (`PROSPECTIVE_ACCOUNT_MISMATCH`), yields `unavailable`. Stored ChargeItems with quantity 0 remain accepted.
